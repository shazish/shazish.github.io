Stage 04

Evidence verification

How Pythia checks cited claims against source text and the contract’s settlement rules.

For regular scans, Pythia reviews the supporting claims behind each remaining CERTAIN classification. Readable evidence, a matching settlement rule, and a current review are all required before finalization can consider the opportunity.

Applies to regular CERTAIN results. STRONG anomalies follow a separate scoring route.

Challenge and verification

Adversarial challenge

A second model pass evaluates counterarguments: an alternative path, settlement ambiguity, or a development that could change the outcome.

If it reports a challenge with strength of at least 70, the script downgrades CERTAIN to LIKELY. This model assessment is distinct from retrieving and checking the cited articles.

Evidence verification

The verifier captures cited pages and reviews their text against each claim and the contract. It records a separate evidence status rather than treating model confidence as proof.

An unverifiable result can retain its CERTAIN label, but finalization withholds it from actionable opportunities.

Verification checks

Code handles eligibility and validation. The model assesses the meaning of the captured text.

Read each verification check
  1. 01

    Citation provenance

    Code

    Each confirming signal needs a structured claim and a full HTTPS citation. That exact URL must appear in the research for the same ticker. A plausible-looking link is not enough.

    Stops here: A missing claim, an invalid URL, or a citation absent from that market’s research.

  2. 02

    Source policy

    Code

    A domain can be trusted, blocked, unknown, or approved as a resolution authority for a specific contract. Blocked domains take precedence. Redirect destinations are checked too.

    Trust is permission to review. It does not establish that an article supports a claim. Unknown domains remain unverifiable; automatic discovery and independent corroboration are not implemented.

  3. 03

    Source capture

    Retrieval + cache

    Fetch the page or reuse a fresh cached copy. The capture records the text, final URL, retrieval time, and a fingerprint of the content. HTML and plain text are supported; PDFs need a readable alternative.

    A successful fetch is not enough. The model must still distinguish substantive reporting from a login screen, paywall, teaser, or error page.

  4. 04

    Settlement matching

    Model review

    The reviewer assesses readability, factual credibility, claim support, settlement match, and timing. It sees the contract’s primary and secondary rules, selected side, closing date, and captured articles.

    The entity, metric, units, threshold, period, and resolution authority must match. A forecast or today’s observation does not establish a future outcome. The reviewer has no browsing tools and treats page contents as data, never instructions.

  5. 05

    Review validation

    Code

    The response must include every expected claim ID, valid verdicts, literal boolean flags, and evidence-specific reasons. Supported and contradicted verdicts need an exact passage of at least 20 characters from the captured text, with whitespace normalized.

    No invented quotations. Malformed responses, missing claims, API errors, and oversized inputs leave pending claims unverified.

Worked example: matching the settlement metric

This fictional example follows one supporting claim. The excerpts below are invented to explain the checks; they are not market data or real source quotations.

Hypothetical contract

Will the first published September index be below 3.0%?

Settlement rule: Use the named statistics office’s first September year-over-year release. Later revisions do not count.

Claim being checked: “The first September year-over-year release is 2.8%, below the threshold.”

Assume the cited URL is in this ticker’s research, the domain is approved, and the release date has passed.

Verified claim

Matching release

“The first release of the September index shows a year-over-year increase of 2.8%.”

The period, metric, release version, and authority match. If the article is readable and credible and the review passes validation, this claim is verified.

Unverifiable claim

Wrong metric

“The September index rose at a 2.8% annualized rate over the latest quarter.”

An annualized quarterly rate is not the required year-over-year rate. This passage does not establish the claim, even though the number looks right.

Contradicted claim

Conflicting release

“The first release of the September index shows a year-over-year increase of 3.2%.”

Readable, credible, time-relevant evidence explicitly conflicts with the 2.8% claim. This is a contradiction, rather than merely a lack of support.

One verified claim is not a verified market. This example isolates a single claim. Every confirming signal on the candidate must pass; the classification must also satisfy its own structural checks.

Verification outcomes

Candidate status is determined by all of its claim checks, with contradictions taking precedence.

Passing verification does not guarantee inclusion. Finalization independently checks that verification still matches the candidate, classification, and source policy. Quote freshness, market availability, estimated edge, sizing, and duplicate-notification checks follow.

Technical details

These implementation details explain how a result can be reviewed later—and why an earlier pass may no longer qualify.

Caching, expiry, and review limits

Captured pages and reviews expire after 24 hours by default. Policy can change either lifetime up to seven days. A review is tied to the candidate and classification, citation, claim, captured content, and source policy; changed inputs require a matching review.

Fresh supported, contradicted, and automatic unverifiable reviews are reused. Fetch failures and model-call or response-validation failures remain retryable. Changing the model alone does not force a new review.

Each candidate’s model request can contain up to 12 pending distinct claims and 60,000 serialized input characters. Articles shared by multiple claims are sent once. Oversized inputs are left unverified instead of silently truncating evidence.

The finalization gate checks the saved verification status, input and policy fingerprints, and evidence/review ages. It does not fetch every article again at that point; cached content may have changed at the publisher since capture.

Artifacts: where the reasoning lives
source_policy.json
Trusted and blocked domains, contract-specific resolution domains, and evidence/review lifetimes.
cache/source_evidence/
Captured text and retrieval metadata, keyed by URL. This is the default location; configuration can relocate it.
evidence_reviews.json
Saved reviews keyed by review ID: verdict, exact excerpt, assessment flags, reason, reviewer, and time.
classified.json → _verification
A separate verification record within each reviewed classification. Confidence and evidence status remain distinct.
verification_report.json
Per-candidate results, claim checks, evidence references, reasons, review errors, and aggregate counts.

Illustrative automatic-review excerpt below. This shows the fields, not a complete runnable artifact; IDs and timestamps are generated during a real run.

{
  "verdict": "supported",
  "excerpt": "The first release of the September index shows a year-over-year increase of 2.8%.",
  "article_accessible": true,
  "evidence_credible": true,
  "settlement_match": true,
  "time_relevant": true,
  "reason": "The first release matches the contract's period, metric and threshold."
}

In automatic review, supported maps to a verified claim only after validation. A supported verdict requires all four flags to be true.

Run modes and interpreting the exit status

From the repository root, replace YOUR_RUN with an existing run folder. These commands review saved classifications; they do not start a new scan.

# Fetch evidence as needed and review pending claims
python3 step_4_verify/verify_classifications.py --run-dir logs/YOUR_RUN

# Fetch evidence, but use saved reviews without model calls
python3 step_4_verify/verify_classifications.py --run-dir logs/YOUR_RUN --manual

# Use fresh cached evidence and saved reviews only
python3 step_4_verify/verify_classifications.py --run-dir logs/YOUR_RUN --offline

--model MODEL selects the review model; otherwise VERIFIER_MODEL or the classifier’s model configuration is used. Automatic review uses the configured model-provider credentials. Manual mode can consume saved human reviews; it does not open an interactive review screen.

Exit 0: all reviewed CERTAIN entries are verified, or no CERTAIN entries exist. Exit 1: at least one is contradicted or unverifiable. Read the report for the reason; a zero exit code alone does not demonstrate that any opportunities were found.

Limits of the evidence check

The model assesses supplied text; it does not independently establish article authenticity or factual truth. Multiple URLs repeating the same announcement do not establish independent corroboration.

Unknown publishers are not automatically investigated or approved. A policy change or an approved alternative source may be needed. Inaccessible articles and PDFs need readable evidence.

The adversarial challenge and anomaly veto are separate model assessments, not equivalent to a successful article-level review. This page describes the regular CERTAIN verification path.
