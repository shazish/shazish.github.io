Pipeline / Classification

Stage 03

Classification

How researched facts become a judgment about a market’s outcome.

For each regular candidate, the classifier weighs evidence against the contract’s settlement rules and time horizon. It records a side, confidence, supporting and contradicting signals, and what could change its conclusion.

Evidence to judgment

The model evaluates a specific contract, rather than predicting a topic in the abstract.

Research supplies the current status, recent developments, and settlement context. With research injected, the API classifier is instructed to use those findings and copy their exact URLs into its signals, rather than repeat the searches.

What the model is asked to consider

Support and contradiction: identify facts that favor the selected side and real evidence against it. The prompt discourages inventing hypothetical objections merely to fill the contradicting-signals list.

Settlement: match the exact metric, units, release version, and definition. A related statistic may answer a different question.

Change conditions: explain the specific evidence or scenario that would invalidate the conclusion. Record settlement ambiguity separately from confidence.

Recent developments: account for late-breaking information. The configured recency window defaults to 14 days. The saved queries and summary are records of research, not proof that a search was executed.

Label and validity are separate

Python checks the structured response after the model answers. A CERTAIN label alone is not enough.

Which checks invalidate, and which downgrade?

Invalid without necessarily changing the label: confidence below 95 for CERTAIN, fewer than three reasons or confirming signals, a missing change condition, or fewer than three saved queries for a non-UNCLEAR result. Errors are recorded in _validation_errors; _valid indicates whether the pass found any errors.

Explicit downgrades: a CERTAIN result with contradicting signals or empty recent developments becomes LIKELY. Detected metric mismatch, certain future-event cases, and the long-horizon check below can also produce LIKELY.

Field checks: confidence must be numeric, and the reasons, signal collections, and query collection must be lists. This is not a complete schema validator: some malformed values can fail before normalization, and checking counts cannot establish the truth of the contents.

Evidence checks happen later: the classifier’s metric guard looks for recognized terms or aliases in the reasoning and signals. It does not read cited articles to establish support. Verification checks those articles against the claims and contract.

Time remaining changes the reasoning

Today’s state may not be the state at settlement. The prompt asks for stronger grounds as the horizon grows.

There is also a code-enforced rule: a CERTAIN candidate with more than 90 days to close and an implied market price below 90¢ is downgraded to LIKELY.

Future-event and metric heuristics

For matching future-event keywords and at least 14 days remaining, the prompt flags the difference between current conditions and the state after the event. The validator checks for forward-looking terms in saved queries and reasons; absence can turn CERTAIN into LIKELY or mark an existing LIKELY result invalid.

These are text heuristics. Mentioning a forecast does not prove the forecast is reliable, and a matching metric keyword does not prove the cited number is correct. Article-level support is checked in verification.

Technical details

What is saved for each candidate
classification · confidence_score · high_confidence_side
The label, model confidence, and selected YES or NO side. Confidence is a model estimate, not a measured success rate.
reasons · confirming_signals · contradicting_signals
The argument and its evidence. Signals pair a fact with a source URL from the research.
recent_developments · searched_for
A recency summary and recorded research queries. UNCLEAR is exempt from the validator’s three-query minimum.
what_would_change_this · settlement_risk
Conditions that could reverse the conclusion, plus possible differences between the real-world event and contract resolution.
_valid · _validation_errors · _model_provenance
Validation outcome, detected problems, and attribution. Candidate data and classification are saved together in classified.json.
Agent-led and API classification

The full runner’s regular path without --model asks the coordinating agent to classify each ticker in context. With an explicit model, it directs classification through the standalone API runner. The standalone script also supports preparing subagent chunks and merging completed results; preparing chunks alone does not classify them.

To explicitly use the API path after research, replace YOUR_RUN with a folder name under the configured log directory, and MODEL with the configured provider’s model ID:

python3 step_3_classification/classify_all.py --run-dir YOUR_RUN --mode api --model MODEL

Here --run-dir takes the run folder name, unlike the verifier’s --run-dir logs/YOUR_RUN path. API classification needs provider credentials.

The API research-injection helper includes the summary and up to six findings and six queries. It instructs the model to reuse this research; the API client does not supply browsing tools. The agent-led path marks missing usable research UNCLEAR, but the standalone API path can still call the model without research.

Retries, checkpoints, and resuming

The API classifier allows a second attempt for malformed JSON or a still-CERTAIN result that fails validation. The outer runner has additional retries for selected API failures; exhausted failures are saved as UNCLEAR.

In API mode, results save after each candidate through a temporary file and atomic replacement. Existing ticker results are skipped on resume. A lockfile checks for overlapping runs. Resume does not automatically reclassify a ticker whose research has changed.

Anomaly candidates use different labels

Anomaly candidates are scored from market data, producing STRONG / WATCH / SKIP. WATCH and STRONG receive a model check for public explanations; a sufficiently confident veto reduces the score and recalculates the tier.

This differs from the regular evidence-based CERTAIN / LIKELY / UNCLEAR path. The anomaly signal score is stored in confidence_score for compatibility, so it should not be read as the regular model’s probability estimate. STRONG anomalies have a separate opportunity route.
